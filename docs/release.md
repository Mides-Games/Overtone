# Cutting a release

Every GitHub release carries executables, not just the source. One local
command builds them; GitHub Actions only deploys (CLAUDE.md, "CI"), so nothing
here runs in Actions.

```bash
.venv/Scripts/python.exe scripts/release.py <version>             # build only: dist/release/<version>/
.venv/Scripts/python.exe scripts/release.py <version> --publish   # build, tag v<version>, GitHub release
.venv/Scripts/python.exe scripts/release.py bump <version>        # set every version at once
```

Windows x64 only: the assets are Windows builds. It needs the venv on
`python/requirements.lock` plus `scripts/requirements-release.txt`
(PyInstaller, pinned), `cargo`, `pnpm` on PATH (or `PNPM` set to it), the Beat
This! model pulled from Git LFS (`git lfs pull`), and, to publish, `gh` signed
in. A missing piece stops the script before it builds anything, named.

## The routine

1. **On `master`, clean.** Stable releases come from production: merge what
   ships into `master` first. `--publish` refuses any other branch, a tree with
   changes in it, or a tag that already exists.
2. **Name the version.** `scripts/release.py bump <version>` writes it
   everywhere it lives (below) and nothing else. Commit that on its own:
   `chore(repo/version): set the version to <version>`.
3. **Head the timeline.** Rename the `Unreleased` entries that ship to the
   version (`## v<version> — <date> · <title>`), so the next release's notes
   start after them and the timeline says which release carried what.
4. **Build and read the dry run.** `scripts/release.py <version>` builds into
   `dist/release/<version>/` and prints the sizes, the smoke test's red lines,
   each step's time and the exact commands `--publish` would run. Read
   `notes.md` there; `--since <tag>` moves where the notes begin.
5. **Publish.** `scripts/release.py <version> --publish` rebuilds from the clean
   tree, tags `v<version>` (annotated), pushes the tag and runs
   `gh release create v<version> --title "Overtone <version>" --notes-file notes.md`
   with the four assets. A version naming `alpha`, `beta` or `rc` is marked
   `--prerelease`; `1.0.0-stable` is not.

The step logs are in `build/release/<version>/logs` (gitignored, like `dist/`).

## The version rule

The product has one version, written in four kinds of place. The script
refuses to build unless all of them equal `<version>`:

| Where | What reads it |
|---|---|
| `Cargo.toml`, `[workspace.package] version` | the Rust crates, and the Python engine: `app_version()` in `python/overtone_paths.py` reads this line, so it is also every written file's `Generated by Overtone v…` header |
| `crates/*/Cargo.toml`, the `overtone-*` path-dependency pins | Cargo, which refuses a pin that does not match |
| `Cargo.lock`, the `overtone-*` entries | Cargo |
| `site/web/package.json` and `site/api/package.json`, `version` | the site's packages |

The tag is `v<version>`, e.g. `v1.0.0-stable`. The script never bumps on its
own: the version is the owner's call.

## The assets

| File | What it is |
|---|---|
| `overtone-cli-<version>-windows-x64.exe` | The v4 Rust engine's command line, one file: `cargo build --release -p overtone-cli`. `overtone-cli analyze song.mp3`. |
| `overtone-engine-<version>-windows-x64.zip` | The v3 Python engine's command line (`python/overtone.py`), the engine the website's worker runs, frozen by PyInstaller (`scripts/overtone-engine.spec`, one folder) into `overtone.exe`. The Beat This! model rides in `assets/models/`, so the beat vote works offline; no Python needed. Unzip and run `overtone.exe song.mp3`. |
| `overtone-site-<version>.zip` | The website for self-hosting: `web/` (the built frontend, `pnpm --dir site/web build`), `api/` (the API's tracked source, without `node_modules` or a `.env`) and `serve.mjs` (`deploy/web/serve.mjs`). `README.txt` inside says how to run it. |
| `SHA256SUMS.txt` | The SHA-256 of the three files above, in `sha256sum`'s format. |

`notes.md` is the release's description and is not uploaded as a file: a
download list, then the `### Changed` bullets of every `docs/timeline.md` entry
added since the previous release tag, each under its entry's title. The
previous tag is the newest `v<semver>` tag other than this version's; where
the clone holds none (the old history's tags live only on the owner's disk),
the notes take every entry above the timeline's newest `## v<version>` heading,
and the script says which cut it made. GitHub refuses a description over
125,000 characters; the script refuses to publish one.

**The smoke test.** Before the engine is zipped, the frozen `overtone.exe` runs
once, as a user who has never run Overtone (a scratch profile; PATH holding
only Windows' own folders, so no Python or developer DLL leaks in), on the
benchmark's `change-128-142` case, rendered by `bench/benchmark.py`'s own code:
128 BPM, then 142 from 30 s. It must print exactly two red lines, each within
the benchmark's 0.05 BPM, under a `Generated by Overtone v<version>` header.
That is one run, not a suite; the gates stay where CLAUDE.md puts them.

## Verifying a download

Download `SHA256SUMS.txt` beside the files, then:

```bash
sha256sum -c --ignore-missing SHA256SUMS.txt                # Linux, macOS, Git Bash
```

```powershell
Get-FileHash .\overtone-engine-<version>-windows-x64.zip   # PowerShell: compare with the line in SHA256SUMS.txt
```

The checksums prove the file is the one the release published, not who built
it: the executables are not code-signed.

## What a release does not verify

- The executables have been run on the build machine only, where the smoke test
  hides Python and the developer PATH but not the machine's other system DLLs.
  A clean Windows without the Visual C++ runtime has not been tried.
- There are no Linux or macOS builds.
- The Rust executable is built, not smoke-tested: the golden and bench modes
  (CLAUDE.md) are its gates.
